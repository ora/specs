# Personal Agent Protocol (PAP) adherence

The Personal Agent Protocol ("Poppy") is developed by Meta and Sierra with industry partners Genesys, Instinct, Rocket, Shopify, Stripe and Walmart (https://sierra.ai/blog/introducing-personal-agent-protocol). Code that publishes, probes, teaches, or grades it must encode the draft correctly in each posture:

| Posture | What it is | Rule |
|---|---|---|
| **Observer** | Code that probes and grades what Companies publish | MAY handle non-conforming forms (an `http://` redirect, a Bearer challenge, an OIDC-only issuer) as detection inputs and finding text. Grades each file by the draft it declares. A 0.4 file is graded by the 0.4 rules as a preview of the in-progress draft, and says so wherever the grade is described. |
| **First-party author** | Your own PAP issuer or published `poppy.json` | MUST be spec-current (the pinned Draft 0.3). |
| **Emitter** | Guidance you hand to the public (recommendations, check catalog text, playbooks, PAP pages, generated `poppy.json` drafts and their notes) | MUST be spec-current (the pinned Draft 0.3; anything about 0.4 is labelled a preview of the in-progress draft): never teach `openid-configuration`, an `http://` endpoint, the token endpoint as an assertion `aud`, or a mechanism Draft 0.3 replaced (`poppy_domains`, Session or Account Tokens, the JWT bearer grant, `session_id`, browser assertions, `auth.direct` / `auth.device` / `auth.mediated` / `auth.custom_scopes`, `poppy:read` / `poppy:write`) unless the same sentence names the older draft it belongs to. |

Which files sit in which posture is repo-specific: see "Repo overlay" below.

**Spec identity.** Personal Agent Protocol **Draft 0.3**, the latest published draft (2026-11-04), read 2026-11-09 at https://personalagentprotocol.org/docs/0.3/spec plus `/docs/0.3/extensions/operations` (operations extension, version 2), `/docs/0.3/extensions/mediated-sign-in` and `/docs/0.3/guides` (recommendations, not normative). Draft 0.3 is the reviewed pin: everything taught or emitted says 0.3. **Draft 0.4** is **in progress** at `/docs/0.4/spec` (and the unversioned `/docs/spec`; operations version 3, `/docs/extensions/browser-control`), read 2026-11-09 at spec repository commit `a2f16ec`; its changelog (https://personalagentprotocol.org/docs/changelog) says the list "grows until 0.4 is published". 0.4 files are graded by the 0.4 rules as a **preview**, labelled as such wherever it is described. Drafts 0.1 (published 2026-10-09) and 0.2 (2026-10-24) are frozen at `/docs/0.1/spec` and `/docs/0.2/spec` and still graded for files that declare them.

The reviewed pin lives in `specs/pap/spec.yaml` of ora/specs and is read through `@ora-ai/specs` (`spec("pap").reviewed`), never restated in code constants. It is pinned on the spec repository (https://github.com/personal-agent-protocol/personal-agent-protocol), not on the rendered pages, whose banners change whenever a new draft starts: the git tree of the pinned draft's folder `content/versions/0.3` (frozen on publication, so it should never move) and the blob of `content/versions/versions.json` (which moves when a draft is published or a new one starts). The unversioned pages that feed graded 0.4 preview rules are pinned as the working draft by a SHA-256 digest of their normalized article text: `/docs/spec`, `/docs/guides`, `/docs/extensions`, `/docs/extensions/operations`, `/docs/extensions/browser-control` and `/docs/extensions/mediated-sign-in`. They 307 to `/docs/0.4/...`, so a moved digest names the 0.4 page that changed, and the 0.4 preview rules it feeds are re-checked then (the in-progress `content/versions/0.4` folder is not pinned: one tree SHA would only say that something moved). Every emitted link opens a versioned `/docs/<version>/...` page, never the unversioned one: frozen for the published drafts 0.1 to 0.3, and the in-progress `/docs/0.4/...` only for what only 0.4 defines, whose anchors can still move. The draft states any part can change incompatibly before 1.0. When asserting anything beyond the pin, re-read the pages and move the pin and this skill together.

## Hard rules (the Draft 0.3 contract, with the 0.4 preview rules - enforce, don't debate)

1. **Discovery is `https://{domain}/.well-known/poppy.json`.** Redirects are followed, every hop is HTTPS, and from Draft 0.3 an agent uses the file only when the last URL's path is exactly `/.well-known/poppy.json` with no query. Outside discovery an agent sends no token, Session header, assertion or credentials to the URL a protocol endpoint redirects to (a MUST from Draft 0.2; Draft 0.1's guides advise it).
2. **`protocol_version` is exact before 1.0.** An agent MUST NOT use a document whose major.minor it does not support. Draft 0.4 adds `supported_versions` (other versions' documents, on the host that served poppy.json; section 3.4, which 0.3 does not have); a 0.3 file that lists it is not graded on it. Every other 0.4-only rule (`tasks.endpoint`, `web.disabled`, `web.unscoped`, `Poppy-Version`, the extension list form, `browser-control`, the website operations endpoint, `poppy:browser-sign-in`) likewise applies to a 0.4 file only.
3. **`organization.domain` is the host that SERVED the document after any redirects**, compared ignoring case only (0.2 and later; 0.1 keeps the requested host, ignoring a leading `www.`).
4. **Every URL the protocol defines or exchanges is HTTPS**, and neither side connects to a loopback, private or link-local address the other gave it.
5. **The issuer.** 0.1 and 0.2 name it in `auth.issuer`. From 0.3 an agent finds it in the RFC 9728 protected resource metadata of `https://{organization.domain}`: a 404 or no `authorization_servers` means no issuer (valid only when `auth.issuer`, `signed_in` access and Mediated Sign-In are absent); one server is the issuer; several need `auth.issuer` to name one; `resource` must be exactly `https://{organization.domain}`; any other answer leaves no fallback. Issuer metadata is RFC 8414 at the path-preserving well-known URL, never `openid-configuration`.
6. **Issuer binding.** Metadata `issuer` matches the issuer character for character. From 0.3: `protected_resources` lists `https://{organization.domain}`, `token_endpoint` and `revocation_endpoint` exist, `grant_types_supported` includes `refresh_token`, plus `authorization_endpoint` for `authorization_code` and `device_authorization_endpoint` for the device grant; ES256 client assertions are accepted; every domain of the issuer selects the same issuer. 0.1 and 0.2 keep `poppy_domains`, `auth.direct` / `auth.device` endpoints, 0.2's ES256 DPoP rule and same-`auth` rule.
7. **Sessions from 0.3.** Every request to APIs, conversations and protocol endpoints carries the `Poppy-Session` JWT; a request that depends on Session claims and has none gets 400 `{"error": "invalid_session"}` (spec 5.3, 7). A POST body needs a request `id` (8.2). Access tokens are plain OAuth, Bearer or DPoP-bound as the Company chooses (RFC 9449 section 5), so Bearer is not a finding for a 0.3 or later file. 0.1 and 0.2 keep their rules (DPoP everywhere except MCP servers without DPoP; Bearer challenges at conversation, operations and feedback endpoints are non-conforming).
8. **MCP servers.** From 0.3, a listed MCP server's protected resource metadata (read only at its own well-known URL, never the origin's) names its `url` as `resource`, and one that offers account access lists the issuer in `authorization_servers`; a server without metadata offers no account access. A 401's challenges carry `resource_metadata`. A server that completes an unauthenticated initialize, refuses it with 400 `invalid_session`, or speaks only MCP 2026-07-28 (400 with an MCP-defined error) has no challenge to grade: read it as not tested, never a failure.
9. **Browser join.** From 0.3: GET the endpoint for a form with a one-time code and a tying cookie, authorize the code at `{endpoint}/authorize` with the Session header, submit the form; a code that fails gets an error status and no cookie. The join page is a 200 with a form holding a `code`, a cookie tying it to the browser (SameSite Strict or Lax; spec 6 says other hosts on the domain MUST NOT be able to set it, and the 0.3 company kit recommends the `__Host-` prefix as a SHOULD), `Cache-Control: no-store`, `frame-ancestors 'none'` (or `X-Frame-Options: DENY`) and a Cross-Origin-Opener-Policy that severs the opener (spec 6 and 10.6, as the 0.3 company kit reads them). `{endpoint}/authorize` without a Session header gets 400 `invalid_session`. 0.1 and 0.2: a junk assertion gets 400 with no cookie.
10. **Probing without credentials (Draft 0.3).** A made-up refresh token sent with the `refresh_token` grant and a junk client assertion should get `invalid_grant`, `invalid_client`, `unauthorized_client` or a DPoP error; every 0.3 issuer supports the grant, so `unsupported_grant_type` is non-conforming. Never re-send the request after a redirect, since spec 3 forbids sending an assertion to the new URL. 0.3 defines no operations endpoint. A 0.4 Company may check `Poppy-Version` before the Session header and answer 400 `version_unsupported`.
11. **Extensions:** plain names belong to the protocol (`operations`; `mediated-sign-in`, `links`, `disclosures`, `ucp` from 0.3; `browser-control` from 0.4); anyone else prefixes a domain (`example.com/gift-wrap`). 0.3 lists one object per extension with a `version`; 0.4 lists an entry per version. Operations is version `"2"` in 0.3 and `"3"` in 0.4 (agents ignore other versions); a 0.4 entry may add an HTTPS `endpoint` only with `web.browser_session_endpoint`, and Browser Control 3 lists `browser-control` together with `web.browser_session_endpoint` but states no MUST. Mediated Sign-In (from 0.3) is an extension whose version 1 entry carries `fields` and `scopes`, whose grant `https://personalagentprotocol.org/grant/mediated-sign-in` the issuer lists. `auth.disabled` is a boolean, and a file that sets it lists neither Mediated Sign-In nor `signed_in` access. A 0.3 `excluded_tasks.url` document has a `tasks` list whose `openapi` or `mcp` references name an API the file lists; 0.4 serves it per Session.

## Unstable areas (feature-detect, never hard-rule)

The protocol is a draft with four eras (0.1 to 0.3 published, 0.4 in progress) and no large production deployments; on 2026-11-09 about 40 public files existed, most declaring 0.1, three declaring 0.3 and none 0.4. Open topics (payments beyond UCP, push notifications, attachments) are undefined, so no check may score them. Guides items are recommendations: never grade them as non-compliance. The grader's own limits never count against a site: a document past a read cap, or a bot shield answering instead of the site, is not the site's answer. The pin is the published 0.3, not the newest draft graded: any code that reads "the pinned version" as "the newest supported version" is wrong. The 0.3 and 0.4 MUSTs a credential-free scan did not yet check are listed in `references/pap-research-2026-11-09.md` section 4.
