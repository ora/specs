# Personal Agent Protocol (PAP) adherence

The Personal Agent Protocol ("Poppy") is developed by Meta and Sierra with industry partners Genesys, Instinct, Rocket, Shopify, Stripe and Walmart (https://sierra.ai/blog/introducing-personal-agent-protocol). Code that publishes, probes, teaches, or grades it must encode the draft correctly in each posture:

| Posture | What it is | Rule |
|---|---|---|
| **Observer** | Code that probes and grades what Companies publish | MAY handle non-conforming forms (an `http://` redirect, a Bearer challenge, an OIDC-only issuer) as detection inputs and finding text. Grades each file by the draft it declares, and a later 1.x minor by the 1.0 rules. The pinned draft (1.0) is the newest one graded, so no file is a preview today; a file declaring a draft newer than the pinned one is graded as a preview of it, and says so wherever the grade is described. |
| **First-party author** | Your own PAP issuer or published `poppy.json` | MUST be spec-current (the pinned Draft 1.0). |
| **Emitter** | Guidance you hand to the public (recommendations, check catalog text, playbooks, PAP pages, generated `poppy.json` drafts and their notes) | MUST be spec-current (the pinned Draft 1.0, always called in progress until it is published, with 0.4 named as the latest published version): never teach `openid-configuration`, an `http://` endpoint, the token endpoint as an assertion `aud`, a mechanism Draft 0.3 replaced (`poppy_domains`, Session or Account Tokens, the JWT bearer grant, `session_id`, browser assertions, `auth.direct` / `auth.device` / `auth.mediated` / `auth.custom_scopes`, `poppy:read` / `poppy:write`), or a poppy.json field Draft 0.4 replaced with `tasks.endpoint` (`excluded_tasks`, `skill_index`; `feedback.endpoint` survives inside the tasks response, spec 9.3) unless the same sentence names the older draft it belongs to. Teach 1.0's forms (0.4's plus the 2026-11-13 fixes): a `description` on every `agent.protocols` entry, ES256 and PS384 accepted, `protocol_version` `"1.0"`, a 0.4 document linked in `supported_versions`, one list entry per extension version, operations version 3, `tasks.endpoint`. |

Which files sit in which posture is repo-specific: see "Repo overlay" below.

**Spec identity.** Personal Agent Protocol **Draft 1.0**, **in progress**. The spec's authors ask builders to use it ("Build against the 1.0 draft, the latest version", https://personalagentprotocol.org/docs/path-to-1), it takes only fixes ("which can include changes that aren't backward compatible", spec 1), and the official company kit validates only `"1.0"`. Read 2026-11-12 at spec repository commit `ad20217`, re-read 2026-11-13 at `bb98332` after eight fixes (`references/pap-research-2026-11-13.md`): https://personalagentprotocol.org/docs/1.0/spec plus `/docs/1.0/extensions/operations` (operations extension, version 3), `/docs/1.0/extensions/mediated-sign-in`, `/docs/1.0/extensions/browser-control` and `/docs/1.0/guides` (recommendations, not normative). On 2026-11-12 1.0 differed from **Draft 0.4** (published 2026-11-10 as the 1.0 release candidate, and the latest published version) only by its version string and a note in spec 10.3 and the guides that nothing in poppy.json confirms the domain belongs to the company `organization.name` names (spec issue #73). On 2026-11-13 1.0 took breaking fixes: each `agent.protocols` entry has a required `description` (spec 8.1), and every Company accepts PS384 client assertions and delegations as well as ES256 (spec 4.1, 5.2); the others (Pushed Authorization Requests, `prompt=consent`, consent pages listing earlier scopes, the same DPoP key at refresh, UCP scope requests naming every scope, ports in `organization.domain`, scope description guidance, room to extend conversations) are not observable without signing in. Everything taught or emitted says 1.0, calls it in progress, and asks a site to also serve 0.4 agents through `supported_versions`. Drafts 0.1 (2026-10-09), 0.2 (2026-10-24), 0.3 (2026-11-04) and 0.4 (2026-11-10) are frozen at `/docs/<version>/spec` and still graded for files that declare them.

The reviewed pin lives in `specs/pap/spec.yaml` of ora/specs and is read through `@ora-ai/specs` (`spec("pap").reviewed`), never restated in code constants; the latest published version is the newest entry of `spec("pap").versions` with a `published` date, never the reviewed one. It is pinned on the spec repository (https://github.com/personal-agent-protocol/personal-agent-protocol), not on the rendered pages, whose banners change whenever a new draft starts: the git tree of the pinned draft's folder `content/versions/1.0` (it moves with every edit to the in-progress draft, and each move means the text taught changed) and the blob of `content/versions/versions.json` (which moves when a draft is published or a new one starts). The unversioned pages that feed graded rules are pinned as the working draft by a SHA-256 digest of their normalized article text: `/docs/spec`, `/docs/guides`, `/docs/extensions`, `/docs/extensions/operations`, `/docs/extensions/browser-control` and `/docs/extensions/mediated-sign-in`. They 307 to `/docs/1.0/...`, so a moved digest names the page that changed. When 1.0 changes a rule, that rule gets a 1.0 branch instead of the 0.4 one. Every emitted link opens a versioned `/docs/<version>/...` page, never the unversioned one; the `/docs/1.0/` pages and their anchors can still change. When asserting anything beyond the pin, re-read the pages and move the pin and this skill together.

## Hard rules (the Draft 1.0 contract: 0.4's rules plus the 1.0 fixes of 2026-11-13 - enforce, don't debate)

1. **Discovery is `https://{domain}/.well-known/poppy.json`.** Redirects are followed, every hop is HTTPS, and from Draft 0.3 an agent uses the file only when the last URL's path is exactly `/.well-known/poppy.json` with no query. Outside discovery an agent sends no token, Session header, assertion or credentials to the URL a protocol endpoint redirects to (a MUST from Draft 0.2; Draft 0.1's guides advise it).
2. **`protocol_version` is exact before 1.0.** An agent MUST NOT use a document whose major.minor it does not support. From 1.0, versions with the same major are compatible (spec 3.4), so a `1.1` file is one a 1.0 agent uses and is graded by the 1.0 rules; `01.0` and `1.00` are not later 1.x minors. Draft 0.4 adds `supported_versions` (other versions' documents, on the host that served poppy.json; section 3.4, which 0.3 does not have); a 0.3 file that lists it is not graded on it. Every other rule 0.4 added (`tasks.endpoint`, `web.disabled`, `web.unscoped`, `Poppy-Version`, the extension list form, `browser-control`, the website operations endpoint, `poppy:browser-sign-in`, `scopes_supported` in the domain's protected resource metadata) likewise applies from 0.4 only. Before 1.0 is published neither a 0.4 nor a 1.0 agent uses the other's file, so a site reaches both by listing the other version's document in `supported_versions`.
3. **`organization.domain` is the host that SERVED the document after any redirects**, compared ignoring case only (0.2 and later; 0.1 keeps the requested host, ignoring a leading `www.`). From 1.0 it carries the served port when that is not 443 (spec 3.1), so compare it against the URL's host with its port, never the bare hostname; the `supported_versions` same-host rule keeps hostnames.
4. **Every URL the protocol defines or exchanges is HTTPS**, and neither side connects to a loopback, private or link-local address the other gave it.
5. **The issuer.** 0.1 and 0.2 name it in `auth.issuer`. From 0.3 an agent finds it in the RFC 9728 protected resource metadata of `https://{organization.domain}`: a 404 or no `authorization_servers` means no issuer (valid only when `auth.issuer`, `signed_in` access and Mediated Sign-In are absent); one server is the issuer; several need `auth.issuer` to name one; `resource` must be exactly `https://{organization.domain}`; any other answer leaves no fallback. Issuer metadata is RFC 8414 at the path-preserving well-known URL, never `openid-configuration`.
6. **Issuer binding.** Metadata `issuer` matches the issuer character for character. From 0.3: `protected_resources` lists `https://{organization.domain}`, `token_endpoint` and `revocation_endpoint` exist, `grant_types_supported` includes `refresh_token`, plus `authorization_endpoint` for `authorization_code` and `device_authorization_endpoint` for the device grant; ES256 client assertions are accepted, and from 1.0 PS384 ones too (`token_endpoint_auth_signing_alg_values_supported` lists ES256, for a 1.0 file PS384 as well, and never `none`; RFC 8414 section 2 requires the list next to `private_key_jwt` or `client_secret_jwt`); every domain of the issuer selects the same issuer. 0.1 and 0.2 keep `poppy_domains`, `auth.direct` / `auth.device` endpoints, 0.2's ES256 DPoP rule and same-`auth` rule.
7. **Sessions from 0.3.** Every request to APIs, conversations and protocol endpoints carries the `Poppy-Session` JWT; a request that depends on Session claims and has none gets 400 `{"error": "invalid_session"}` (spec 5.3, 7). A POST body needs a request `id` (8.2). At an entry with `access: signed_in` a 401 asking for an account may come first (3.2 and 7 set no order between that check and the Session check). Access tokens are plain OAuth, Bearer or DPoP-bound as the Company chooses (RFC 9449 section 5), so Bearer is not a finding for a 0.3 or later file. 0.1 and 0.2 keep their rules (DPoP everywhere except MCP servers without DPoP; Bearer challenges at conversation, operations and feedback endpoints are non-conforming).
8. **MCP servers.** From 0.3, a listed MCP server's protected resource metadata (read only at its own well-known URL, never the origin's) names its `url` as `resource`, and one that offers account access lists the issuer in `authorization_servers`; a server without metadata offers no account access. A 401's challenges carry `resource_metadata`. A server that completes an unauthenticated initialize, refuses it with 400 `invalid_session`, or speaks only MCP 2026-07-28 (400 with an MCP-defined error) has no challenge to grade: read it as not tested, never a failure.
9. **Browser join.** From 0.3: GET the endpoint for a form with a one-time code and a tying cookie, authorize the code at `{endpoint}/authorize` with the Session header, submit the form; a code that fails gets an error status and no cookie. The join page is a 200 with a form holding a `code`, a cookie tying it to the browser (SameSite Strict or Lax; spec 6 says other hosts on the domain MUST NOT be able to set it, and the 0.3 company kit recommends the `__Host-` prefix as a SHOULD), `Cache-Control: no-store`, `frame-ancestors 'none'` (or `X-Frame-Options: DENY`) and a Cross-Origin-Opener-Policy that severs the opener (spec 6 and 10.6, as the 0.3 company kit reads them). `{endpoint}/authorize` without a Session header gets 400 `invalid_session`. 0.1 and 0.2: a junk assertion gets 400 with no cookie.
10. **Probing without credentials (Draft 0.3).** A made-up refresh token sent with the `refresh_token` grant and a junk client assertion should get `invalid_grant`, `invalid_client`, `unauthorized_client` or a DPoP error; every 0.3 issuer supports the grant, so `unsupported_grant_type` is non-conforming. Never re-send the request after a redirect, since spec 3 forbids sending an assertion to the new URL. 0.3 defines no operations endpoint. From 0.4 a Company may check `Poppy-Version` before the Session header and answer 400 `version_unsupported`.
11. **Extensions:** plain names belong to the protocol (`operations`; `mediated-sign-in`, `links`, `disclosures`, `ucp` from 0.3; `browser-control` from 0.4); anyone else prefixes a domain (`example.com/gift-wrap`). 0.3 lists one object per extension with a `version`; from 0.4 a list with an entry per version. Operations is version `"2"` in 0.3 and `"3"` from 0.4 (agents ignore other versions); from 0.4 an entry may add an HTTPS `endpoint` only with `web.browser_session_endpoint`, and Browser Control 3 lists `browser-control` together with `web.browser_session_endpoint` but states no MUST. Mediated Sign-In (from 0.3) is an extension whose version 1 entry carries `fields` and `scopes`, whose grant `https://personalagentprotocol.org/grant/mediated-sign-in` the issuer lists. `auth.disabled` is a boolean, and a file that sets it lists neither Mediated Sign-In nor `signed_in` access. A 0.3 `excluded_tasks.url` document has a `tasks` list whose `openapi` or `mcp` references name an API the file lists; from 0.4 it is served per Session. **Scopes (published 0.4, spec 3.2 and 4.7):** the scopes an agent can request may be in the issuer's `scopes_supported`, in the `scopes_supported` of the domain's protected resource metadata, or both, and agents read them as one list; a 0.3 file has only the issuer's list.

## Unstable areas (feature-detect, never hard-rule)

The protocol is a draft with five eras (0.1 to 0.4 published, 1.0 in progress) and no large production deployments; on 2026-11-09 about 40 public files existed, most declaring 0.1, three declaring 0.3 and none 0.4 (`references/pap-research-2026-11-12.md` section 1 has the 2026-11-12 recheck). Open topics (payments beyond UCP, push notifications, attachments) are undefined, so no check may score them. Guides items are recommendations: never grade them as non-compliance. The grader's own limits never count against a site: a document past a read cap, or a bot shield answering instead of the site, is not the site's answer. The pin (1.0) is the newest draft graded today, but it is not published: code that needs the latest published version reads it from the versions with a `published` date, never from the reviewed version. The MUSTs a credential-free scan does not check yet are listed in `references/pap-research-2026-11-09.md` section 4, `references/pap-research-2026-11-12.md` section 4 and `references/pap-research-2026-11-13.md`.

## Repo overlay

Each consuming repo keeps its own posture table (which of its files are observer, first-party author, or emitter), its check ids, its probe budget and any reserved URLs, and its own enforcement (mechanical adherence suites, reviewers) in its own rules file, alongside its grading decisions. On repo-specific points, the overlay wins over this skill.
