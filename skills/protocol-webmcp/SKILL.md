# WebMCP protocol adherence

Code that registers, teaches, or scores WebMCP tools must encode the spec correctly in three distinct postures. Confusing them is the root of most divergence:

| Posture | What it is | Rule |
|---|---|---|
| **Observer** | Code that detects what sites in the wild ship, including legacy APIs (capture shims, static signal readers, audit checks, fixtures) | MAY reference removed/deprecated APIs as detection signatures and finding text. Never as recommended usage. |
| **First-party author** | Your own registered tools | MUST be spec-current (rules below). |
| **Emitter** | Code you hand to the public as guidance (fix snippets, suggested tool code, docs) | MUST be spec-current. Everything here teaches other sites; a stale API in a fix snippet propagates the break to the whole audience. |

Which files sit in which posture is repo-specific: see "Repo overlay" below.

**Spec identity.** W3C Web Machine Learning CG draft at https://webmachinelearning.github.io/webmcp/ - a CG-DRAFT, not a W3C Standard, and NOT a wire implementation of Anthropic's MCP (it borrows vocabulary only; no JSON-RPC, no HTTP transport, no initialize handshake). Pinned snapshot: **10 November 2026** (previous pin 4 November 2026). The reviewed pin (version, read date, and sources with the `index.bs` blob SHA) lives in `specs/webmcp/spec.yaml` of ora/specs and is read through `@ora-ai/specs` (`spec("webmcp").reviewed`), never restated in code constants. Precedence: **the spec wins over Chrome's preview** - Chrome lag is something to note as implementation lag, never the contract to generate against. When asserting anything beyond the snapshot date, re-read the rendered spec first, and move the pin and this skill together.

## Hard rules (survived the 2026 churn - enforce, don't debate)

1. **Entry point is `document.modelContext`.** `navigator.modelContext` appears only as a trailing fallback alias in the canonical feature-detect: `document.modelContext || navigator.modelContext`. Never navigator-first, never navigator-only.
2. **Unregistration is ONLY the AbortSignal passed to `registerTool(tool, { signal })`.** `unregisterTool()`, `provideContext()`, `clearContext()`, `window.agent`, `document.agent` are removed APIs. Never generate them, never recommend them (stale Feb-May 2026 blogs and training data still teach them).
3. **Name grammar:** 1-128 chars, ASCII alphanumeric + `_` + `-` + `.` only. No slashes (MCP-style `github/search` names are illegal), no spaces, no Unicode.
4. **`inputSchema` is a JSON Schema 2020-12 JavaScript object, never a pre-stringified JSON string.** The UA does not validate args against it before calling `execute` (spec issue 92) - validate inside `execute`. `title` is a top-level tool member (localized), never an annotation. A non-object `inputSchema` or `outputSchema` (such as `""`) makes `registerTool()` throw a `TypeError`.
5. **`execute(inputObject, { signal })`** receives a parsed object and MUST honor the signal. Return value must be JSON-serializable (no DOM nodes, functions, BigInt, circular refs). Rejection reasons are NOT surfaced to the caller - put recovery hints in a successful JSON return. Since 8 Oct 2026 the caller sees specific `DOMException` names, never `UnknownError`: `NotFoundError` (tool not found, origin mismatch, or not exposed), `DataError` (input does not parse to an Object - arrays pass), `OperationError` (execute rejected, or result not JSON-serializable), `AbortError` (target document unloaded). Unregistering does not cancel an execution already running. `executeTool` has further rejections of its own (`InvalidStateError`, `NotAllowedError`, `NotSupportedError`, the abort reason, and `TypeError` for a non-dictionary argument): reference section 4.6.
6. **Annotations are exactly `{ readOnlyHint, untrustedContentHint, consequentialHint, debugging }`**, all booleans defaulting to `false`. `consequentialHint: true` marks significant, real-world, or irreversible actions (booking, payment, transfer) so an agent can ask the user first - it is WebMCP's own answer where MCP code reaches for `destructiveHint`. `debugging: true` marks developer-only tools. `destructiveHint`, `idempotentHint`, `openWorldHint`, `annotations.title`, MCP content-block envelopes, prompts, resources are MCP vocabulary that does not exist in WebMCP. Observed in the wild? That is an observer finding. Recommended or emitted? Bug. Code that captures or projects tool declarations must carry all four WebMCP keys; dropping one hides a spec-current declaration.
7. **`outputSchema` is a WebMCP tool member since 2 Nov 2026** (spec #254): an optional JSON Schema object describing the result, deep-copied at registration and returned parsed by `getTools()`; agents may reject results that do not validate against it. It is spec-current, never an MCP-vocabulary mistake. Whether a check scores it is a consumer decision, not a spec rule.
8. **Events fire at `document.modelContext`, all UA-fired.** `toolchange` carries no tool list (listeners re-call `getTools()`; pages never `dispatchEvent` it by hand). `toolactivated` (`ToolActivatedEvent.toolName`) fires right after `execute` is invoked, even when it throws (webmcp #371, 2026-11-09; earlier drafts fired it just before); `toolcancel` (`ToolCancelEvent.toolName`, never `toolcanceled`) fires when a pending execution is cancelled. None of them fire on `window`.
9. **Permissions Policy token is `tools`** (default allowlist `self`; cross-origin iframes need `allow="tools"`; `Permissions-Policy: tools=()` is the documented opt-out for a document and all its frames). There is no `model-context` token. Secure context required. The origin-keyed agent cluster requirement was REMOVED on 30 Sep 2026 - do not state it as a WebMCP precondition (still never suggest `document.domain`, which is deprecated platform-wide).
10. **Cross-origin sharing is a two-sided opt-in:** `exposedTo` (the tool owner names the callers it allows) and `fromOrigins` (the caller names the origins it takes tools from), potentially-trustworthy origins only; section 6.3.4 (27 Oct 2026) explains why both sides are required.
11. **No transport.** No WebMCP HTTP header, well-known URL, or manifest exists. A bare probe cannot detect WebMCP; only a live page can, so detection needs a real browser that loads the page.

## Unstable areas (feature-detect, mark as preview, never hard-rule)

**Declarative form attributes are not in the spec at all**: the 8 Oct 2026 draft removed the declarative section (it was a TODO); the README lists it as future exploration in a separate explainer, and only Chrome's origin trial implements it. Observe and report `<form toolname>`, never present it as specified WebMCP. Also unstable: `executeTool` argument encoding and `getTools().inputSchema` type (spec says object, Chrome 151 still uses strings - accept both when consuming), `requestUserInput`, native validation of results against `outputSchema`, Service Worker tools, streaming/multimodal I/O, `updateTool()` / lazy schemas (none exist), missing-`title` representation (issue 224). Full list: `references/webmcp-research-2026-10-16.md` section 5.

## Repo overlay

Each consuming repo keeps its own posture table (which of its files are observer, first-party author, or emitter) and its own enforcement (mechanical adherence suites, reviewers) in its own rules file, alongside any decisions it makes about what to score. On repo-specific points, the overlay wins over this skill.
